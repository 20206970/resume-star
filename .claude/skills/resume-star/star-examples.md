# STAR Examples Reference

## STAR Format Definition

- **S (Situation):** 项目背景和面临的挑战（1句话）
- **T (Task):** 你负责的具体任务（1句话）
- **A (Action):** 你采取了什么行动，用了什么技术（2-3句话，这是核心）
- **R (Result):** 产生了什么结果，尽量量化（1句话）

## Bullet Point 写法规则

每条分点描述必须遵循以下结构:

### 结构: 动词开头 + 做了什么 + 怎么做的 + 效果/指标

1. **动词开头:** 以"设计并实现"、"开发"、"构建"、"优化"、"实现"、"面向"等动词起头，不用"参与了"、"负责了"等弱动词
2. **做了什么:** 一句话说清楚核心目标（设计什么、解决什么问题）
3. **怎么做的:** 列出关键技术方案和工具（不是堆名词，而是说明怎么用的）
4. **效果/指标:** 量化结果放在句末；如果没有量化数据，用定性成果（"统一了…流程"、"提升了…效率"）

### 示例拆解

> 设计和实现面向LLM的可靠性评测基础设施，围绕HuggingFace/vLLM等执行框架，统一故障注入、运行观测与因果归因流程。

- 动词开头: "设计和实现"
- 做了什么: "面向LLM的可靠性评测基础设施"
- 怎么做的: "围绕HuggingFace/vLLM等执行框架"
- 效果: "统一故障注入、运行观测与因果归因流程"

### 长度要求
- 每条 1-3 行，信息密度要高
- 不要为了简洁而丢失技术细节，宁可写长一点也要把"怎么做的"说清楚

## Good Examples

### Example 1: 课程项目 — 编译器

**简历分点描述（可直接复制）:**
> 设计并实现支持泛型类型推断的 Mini-Java 编译器前端，基于 ANTLR4 构建语法树并手写 Visitor 模式实现类型推断算法，通过单元测试覆盖 50+ 边界用例，最终通过全部 200 个测试用例，类型推断准确率 98%

**STAR 展开（面试准备）:**
- **背景:** 在编译原理课程中，需实现一个支持类型推断的 Mini-Java 编译器前端
- **任务:** 负责语法分析器和类型检查模块的设计与实现
- **行动:** 使用 ANTLR4 构建语法树，手写 Visitor 模式实现类型推断算法，支持泛型和继承的类型检查
- **结果:** 通过全部 200 个测试用例，类型推断准确率 98%，获得课程最高分

---

### Example 2: 实习项目 — 工单系统优化

**简历分点描述（可直接复制）:**
> 优化内部工单系统分配逻辑，分析工单数据发现分配规则瓶颈，重新设计基于技能标签的智能匹配算法，将工单自动分配率从 30% 提升至 85%，平均处理时间从 48 小时降至 12 小时

**STAR 展开（面试准备）:**
- **背景:** 实习期间，公司内部工单系统响应缓慢，平均处理时间超过 48 小时
- **任务:** 负责优化工单分配逻辑，提升处理效率
- **行动:** 分析工单数据发现分配规则不合理，重新设计基于技能标签的智能匹配算法
- **结果:** 自动分配率从 30% 提升至 85%，平均处理时间从 48 小时降至 12 小时

---

### Example 3: 个人项目 — 校园二手交易平台

**简历分点描述（可直接复制）:**
> 独立开发校园二手交易微信小程序，基于 Vue.js + 微信云开发实现商品发布、搜索、收藏、聊天全流程，集成微信支付模拟流程，上线 2 周获注册用户 500+，促成 100+ 笔交易

**STAR 展开（面试准备）:**
- **背景:** 校园内缺乏统一的二手交易平台，学生依赖微信群发布信息
- **任务:** 独立开发一个校园二手交易微信小程序
- **行动:** 使用云开发 + Vue.js，实现商品发布、搜索、收藏、聊天功能，集成微信支付模拟流程
- **结果:** 上线 2 周内注册用户 500+，日均活跃用户 80+，促成 100+ 笔交易

---

### Example 4: 科研项目 — LLM 可靠性评测（参考范例）

**简历分点描述（可直接复制）:**
> 设计和实现面向LLM的可靠性评测基础设施，围绕 HuggingFace/vLLM 等执行框架，统一故障注入、运行观测与因果归因流程

> 面向不同后端在量子执行、调度方式、KV Cache 管理上的差异，抽象统一接口与故障四元组表示（定位、时序、扰动、空间模式），提升多模型、多后端适配效率

> 在保持较强可扩展性的前提下，将注入框架开销控制在 <1%，全链路观测开销控制在 5%-10%

## Bad Examples (要避免)

### ❌ 弱动词开头
> 参与了电商项目的开发，负责后端模块
> 负责了用户系统的设计和开发

问题: "参与了"、"负责了"是弱动词，没有说明具体做了什么。改用"设计并实现"、"开发"、"构建"等强动词。

### ❌ 太笼统
> 参与了电商项目的开发，负责后端模块

问题: 没说做了什么、用了什么技术、有什么成果

### ❌ 只列技术名词
> 使用了 Spring Boot + MySQL + Redis + RabbitMQ

问题: 堆技术名词但不说明解决了什么问题

### ❌ 假大空的结果
> 大幅提升了系统性能，获得了领导和同事的一致好评

问题: 没有量化数据，"好评"不是有效结果

### ❌ 抄袭模板痕迹重
> 运用敏捷开发方法论，通过 Scrum 框架推动团队高效协作...

问题: 在校生项目不需要这种企业级话术，面试官一看就知道是编的

### ❌ 过于简短丢失细节
> 实现了编译器前端，用了 ANTLR4

问题: 虽然动词正确，但信息密度太低，没有说明"做了什么"和"效果"

## Quantification Tips

在校生项目可能觉得没有数据可量化，以下思路可以帮助找到量化角度:

| 场景 | 量化角度 |
|------|---------|
| 课程项目 | 测试用例数量、代码行数、功能模块数、覆盖的边界情况 |
| 性能优化 | 响应时间变化、内存占用变化、支持的数据量 |
| 功能开发 | 完成的功能点数量、支持的用户操作数 |
| 个人项目 | 用户数、日活、交易量、页面浏览量 |
| 实验项目 | 准确率/精确率/召回率、实验数据集规模 |
| 团队项目 | 团队规模、你负责的模块占总模块的比例 |

## 量化规则

生成 STAR 时对 Result 部分遵循以下原则:

1. **优先量化:** 如果能从项目信息中推断出数字，必须量化展示
   - 有具体数字的 Result: "通过全部 200 个测试用例，类型推断准确率 98%"
   - 能推断规模的: "独立完成 3 个核心模块的开发，占项目总代码量约 40%"
2. **不可编造:** 如果确实没有数据，用定性描述，不编数字
   - 可接受的无数据 Result: "编译器成功支持完整的 Mini-Java 语法，通过全部课程验收测试"
   - 不可接受: "性能提升了 200%"（无依据）
3. **量化来源:** 从项目扫描结果中提取
   - 目录/文件数量 → 模块数、代码规模
   - 测试文件 → 测试用例数
   - README 描述 → 功能点数、用户数
   - 配置文件 → 依赖/集成数量

## Output Format

最终输出**分两部分，分点描述在前（用户最需要），STAR 展开在后（面试准备）:**

```markdown

以下分点描述可直接粘贴到简历中:

1. [动词开头] [做了什么]，[怎么做的/关键技术方案]，[效果或量化指标]
2. [动词开头] [做了什么]，[怎么做的/关键技术方案]，[效果或量化指标]
3. [动词开头] [做了什么]，[怎么做的/关键技术方案]，[效果或量化指标]

---

## STAR 展开说明（面试准备用）

### 1. [亮点关键词]
- **背景:** [项目背景和挑战]
- **任务:** [你的具体职责]
- **行动:** [你做了什么、用了什么技术]
- **结果:** [量化结果或定性成果]

### 2. [亮点关键词]
- **背景:** [...]
- **任务:** [...]
- **行动:** [...]
- **结果:** [...]

### 3. [亮点关键词]
- **背景:** [...]
- **任务:** [...]
- **行动:** [...]
- **结果:** [...]
```
