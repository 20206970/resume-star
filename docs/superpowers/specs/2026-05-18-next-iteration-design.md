当前 `resume-star` Skill 的 7 模块扩展（A1-A4, B1-B3）已全部实现并同步。本轮在此基础上深化。

## P0: 代码证据链

**目标:** 每个项目亮点附带关键源文件路径，提升生成内容可信度，方便面试时解释来源。

**改动文件:** `resume-star/project-scan.md`

**设计:**

在项目扫描阶段，识别到每个亮点时同时记录其代码证据：

```markdown
亮点：实现统一异常处理，提高接口错误响应一致性

证据：
- src/main/java/com/example/common/GlobalExceptionHandler.java
- src/main/java/com/example/common/Result.java

可写入简历：
- 封装统一响应体与全局异常处理机制，提升接口返回规范性和前后端联调效率。
```

**证据来源优先级:**
1. 直接从 Glob/Grep 命名推断（如文件名含 `ExceptionHandler`、`Cache`、`Auth`）
2. 从 README / 配置文件中提取的功能描述
3. 从目录结构推断的模块职责

**规则:**
- 证据必须是项目扫描阶段真实发现的文件，不能凭 JD 推测编造
- 每个亮点最多列出 3 个关键文件路径
- 如果扫描阶段无法定位具体文件（如用户无本地项目），该亮点标记为"基于用户描述"

## P0: Git 贡献分析

**目标:** 利用 git log 识别用户实际负责的模块，区分个人贡献与团队贡献，提升简历真实性。

**改动文件:** `resume-star/project-scan.md`, `resume-star/SKILL.md`

**设计:**

### 扫描阶段新增 Git 分析步骤

在 project-scan.md 的扫描序列末尾增加 git 分析：

```bash
git log --oneline -20          # 最近 20 条提交概览
git log --stat --oneline -10   # 带文件变更的提交记录
git shortlog -sn               # 按作者统计提交数
```

### 分析输出

```markdown
## Git 贡献分析

- 开发周期：2024.03 - 2024.05
- 总提交数：86（用户占 52）
- 高频修改模块：用户认证、简历编辑器、PDF 导出
- 主要贡献：完成用户登录、简历数据结构设计、导出逻辑实现
```

### 在 SKILL.md 中的流程变更

项目扫描阶段增加一个确认步骤：

> "我分析了项目的 Git 记录。看起来你主要贡献了 [模块列表]。这样理解对吗？如果项目不是你一个人的，告诉我你负责的部分。"

**规则:**
- 仅在项目是 git 仓库时执行（非 git 项目跳过，不报错）
- 如果多人贡献，主动提醒用户确认个人负责范围
- 统计数据仅作为参考，最终以用户确认为准
- 不分析具体代码 diff 内容（节省 token），只看文件路径和提交频率

## P1: 项目亮点分类

**目标:** 将项目亮点按维度分类，支持用户选择突出方向，匹配不同岗位侧重点。

**改动文件:** `resume-star/project-scan.md`, `resume-star/star-examples.md`

**设计:**

### 分类维度

```text
技术亮点     — 技术选型、架构设计、技术难点解决
性能亮点     — 响应时间、吞吐量、资源优化
工程化亮点   — 代码规范、CI/CD、测试、错误处理
业务亮点     — 功能完整度、用户体验、业务闭环
安全亮点     — 认证鉴权、数据保护、输入校验
数据亮点     — 数据处理规模、数据流设计、存储优化
```

### 输出格式

```markdown
## 项目亮点（按维度分类）

### 技术亮点
- 使用 Redis 缓存热点数据，降低数据库访问压力
- 采用 JWT 完成无状态登录鉴权

### 工程化亮点
- 封装统一响应结构和异常处理机制
- 基于 Git 分支管理完成多人协作开发

### 业务亮点
- 实现用户注册、登录、简历编辑、导出完整闭环
```

### 在 STAR 生成阶段的应用

当用户提供了 JD 后，Skill 根据岗位类型自动推荐优先突出的维度：

| 岗位类型 | 优先突出的亮点维度 |
|---|---|
| 后端开发 | 技术亮点 > 性能亮点 > 工程化亮点 |
| 前端开发 | 业务亮点 > 技术亮点 > 用户体验 |
| 算法/数据 | 数据亮点 > 技术亮点 > 性能亮点 |
| 产品经理 | 业务亮点 > 数据亮点 |
| 测试开发 | 工程化亮点 > 技术亮点 |

用户也可手动指定："重点突出工程化方面的亮点"。

## P2: 简历子弹点质量评分

**目标:** 对生成的每条 STAR 描述进行自评，给出改进建议，形成反馈闭环。

**改动文件:** `resume-star/star-examples.md`, `resume-star/SKILL.md`

**设计:**

### 评分维度

```markdown
## 子弹点质量评分

| 维度 | 满分 | 说明 |
|------|------|------|
| 完整性 | 10 | 是否包含动词 + 做了什么 + 怎么做 + 结果 |
| 岗位匹配度 | 10 | 是否命中 JD must-have 技能 |
| 技术含量 | 10 | 是否有具体技术细节，而非空泛描述 |
| 量化程度 | 10 | 结果是否有数据支撑（无数据不扣分，编造数据直接标红） |
| 面试可解释性 | 10 | 用户是否能在面试中复述并解释 |
```

### 输出格式

在 STAR 生成输出末尾附上：

```markdown
---

## 质量评估

| # | 完整性 | 匹配度 | 技术含量 | 量化 | 可解释性 | 建议 |
|---|--------|--------|----------|------|----------|------|
| 1 | 8/10   | 9/10   | 7/10     | 5/10 | 8/10     | 补充接口响应速度或代码复用率 |
| 2 | 9/10   | 8/10   | 8/10     | 7/10 | 9/10     | 良好 |
| 3 | 7/10   | 6/10   | 6/10     | 3/10 | 7/10     | 结果部分偏空泛，建议补充功能覆盖范围 |

**整体建议:** 第 3 条描述的量化程度最低，可补充"覆盖 X 个接口"或"支持 Y 种导出格式"。
```

### 规则

- 评分在生成 STAR 后自动附带，不需要用户额外触发
- 评分基于内容本身质量，不受项目大小影响（小项目也可以高分）
- 编造数据检测：如果量化数据无法从项目扫描结果中找到来源，标记为"⚠️ 量化数据来源不明，建议确认"
- 用户可以要求"重新生成得分最低的那条"

## P3: JD 风格策略表

**目标:** 根据公司类型和 JD 风格自动调整简历表达策略，提升匹配度。

**改动文件:** `resume-star/jd-analysis.md`

**设计:**

### 风格分类与策略

| JD 风格 | 识别信号 | 表达策略 |
|---|---|---|
| 大厂校招型 | "校招"、"应届"、"2025届"、"培养体系" | 强调基础扎实、学习能力、项目完整度、工程规范 |
| 创业公司实战型 | "0到1"、"快速迭代"、"多面手"、"全栈" | 强调独立负责、快速交付、业务结果、跨职能 |
| 技术深度型 | "原理"、"源码"、"优化"、"架构设计"、"底层" | 强调技术难点、方案对比、性能数据、架构决策 |
| 业务导向型 | "用户体验"、"业务价值"、"数据驱动"、"增长" | 强调业务闭环、用户影响、数据指标、产品思维 |
| 外企英文型 | 英文 JD、global team、"communication" | 英文输出、职责边界清晰、结果导向、避免堆砌技术词 |
| 工程规范型 | "CI/CD"、"代码审查"、"测试覆盖"、"SOP" | 强调工程化实践、代码质量、协作流程、文档习惯 |

### 在 JD 解析阶段的输出

在岗位画像末尾附加：

```markdown
### JD 风格判断
- 风格：大厂校招型
- 信号词：校招、应届、培养体系
- 建议表达重点：基础扎实、项目完整度、学习能力
```

### 在 STAR 生成阶段的应用

Skill 根据风格自动调整 Bullet Point 的侧重点（不需要用户手动指定）。例如同一个 Redis 缓存的亮点：

- 大厂校招型："学习并应用 Redis 缓存机制，降低数据库查询频率，提升系统响应速度"
- 技术深度型："基于 Redis 设计多级缓存策略，通过缓存预热和懒加载机制降低数据库查询压力约 60%"
- 创业实战型："独立完成 Redis 缓存模块，上线后首页加载速度显著提升"
